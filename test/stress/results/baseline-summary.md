# kubesentry baseline stress test (Phase 0, levels L1 to L3)

Run on 2026-10-11 against the code tagged `baseline` (images built before any Phase 1 change), deployed by `hack/kind-up.sh` with the shipped settings: one replica, memory limit 256Mi, client-go defaults, `-audit-log-file` with `-audit-from-start`, MemoryStore of 50,000 audit events. The cluster is kind on Kubernetes 1.36.4 (1 control plane, 5 workers, worker 5 reserved for load generators) plus KWOK fake nodes with EKS labels. Per the user's decision the run stops at **L3** (500 fake nodes, 10,002 pods); L4 stays defined in the generator but was not run. The host guard never had to stop anything: the lowest available memory was 3,472 MiB (during the L3 verifier), against the 1,536 MiB floor.

Per-level details: `baseline-L1/report.md`, `baseline-L2/report.md`, `baseline-L3/report.md` (and `assoc.md`, `conn.md`, the JSON files and job logs next to them). The tables after the findings are generated by `stress summary`.

## Findings

1. **Client-side throttling sets the ceiling, and it is reached by one user.** Every API request runs full paginated LISTs (500 per page). client-go's defaults (QPS 5, burst 10) apply per API-group client (core, apps, batch, networking, rbac, storage, dynamic), so kubesentry's request rate to the API server plateaus at about 5–8 per second whatever the number of users (busiest minute 13.8/s). Single-user page latency therefore grows linearly with the pod count: about 0.55 ms per pod for the map (1.6 s → 3.0 s → 5.8 s from 2k to 10k pods), and the same slope for nodes, workloads and security. Under load the requests queue on the limiter: at L3 with 1Gi, even 10 users never see `/oom`, `/pvcs/unused`, `/security` (all 60 s polls), `/pods`, `/map` or `/nodes` (30 s polls) complete before the next poll replaces them. The API server itself is not the bottleneck: kubesentry's LISTs take p50 3–14 ms and p99 21–29 ms server-side (audit log), and the API server never returned 429.
2. **256Mi is not enough, and an OOM costs minutes.** kubesentry was OOMKilled at 50 users on L1, at 10 users on L2 and L3, while answering audit queries after a 1M-event ingest (all levels), and when 500 agents post at the same instant (all levels). Each restart lands in CrashLoopBackOff (up to 5 minutes), loses the in-memory audit store and every agent's process report, and replays the whole audit log from the start (`-audit-from-start`, 50–100 MB files here). The memory peaks are short (cAdvisor at 30 s saw 249–254 MiB maxima); no GOMEMLIMIT is set, so the Go heap grows to twice the live set before collecting. With 1Gi there were no OOM kills during the user ramps (max 326 MiB), which isolates throttling as the second, independent failure.
3. **The user-count target is far away.** Highest passing stage: 10 users at L1; 10 users at L2 only with 1Gi; none at L3. The 2,000-user goal was only reachable as a load level (at L2 the first ramp ran to 2,000 users with 95–100% errors).
4. **Association is right for ordinary workloads and wrong exactly where selectors and ownership diverge.** All generated namespaces matched the ground truth (selector-based ownership works when selectors are unique); precision and recall are ≥ 99.6% everywhere. The 13 failing expectations are the same at every level: overlapping selectors (the canary pod is shown under `web`, `web` counts 3 pods instead of 2, the canary Deployment gets no security finding); Jobs with a manual, shared selector (both pods under `manual-a`); orphaned ReplicaSets, pods owned by a custom resource, and a Rollout-like owner (no owner shown; security findings fall back to one per pod); a Deployment's pod count includes a terminating pod; an unready pod shows status ok; a Succeeded pod that the EndpointSlice still lists (not ready, not serving) is not shown. Passing cases: Jobs with identical labels but generated selectors, a 300-pod Service over 3+ EndpointSlices, multi-workload Services, a mid-rollout Deployment, static and bare pods, unschedulable, CrashLoopBackOff and ImagePullBackOff pods (warn), PVC mounts, an Ingress to a missing Service, CronJob → Job.
5. **Connectivity and data sources are healthy.** 108/108 probes per level (pod→pod across all 6 real nodes, pod and host network, ClusterIP, Service DNS, and kubesentry's Service from every node); kubesentry reaches Prometheus (`/oom?window=1h` 0.2 s → 0.6 s → 3.3 s); the real agents are fresh on all 6 nodes. Prometheus also tries to scrape kube-proxy on every fake node (100–500 targets down, "no route to host"): `kps-values.yaml` drops only the fake kubelet targets.
6. **Audit ingest is fast; the store is the problem.** 1M events (858 MB of EventLists, 0.5% duplicates, exec stage pairs, every tag) went in at the target 3,000/s with webhook p99 ≤ 32 ms and no failed batch at every level, and the Findings query during ingest stayed under 105 ms p99. After ingest, at 256Mi, kubesentry was OOMKilled by the next few queries; with 1Gi (L3) every query over the full 50k store answered in p99 3–299 ms (`includeReads` with limit 1000 is the slowest; `summary?since=24h` 174 ms). The 50k cap means the store holds about 17 seconds of this firehose.
7. **Agents are cheap when spread, fatal when synchronized.** 500 agents with fixed random phases (33 posts/s, 100–125 KB each, 3–4 MB/s) were all accepted in ≤ 2 ms p99 at every level. The same 500 posting at the same instant (as after a DaemonSet rollout; the baseline agent has no jitter) OOM-killed kubesentry on every level (49–70% accepted, the rest refused or timing out), after which no pod had process data.
8. **`/oom` will exceed its 64 MiB read cap at about L3–L4.** The range query kubesentry issues for the 24h window returned 31–39 bytes per point; with 24h of history (240 points per series) the answer is 21 MB at L1, 41 MB at L2 and 81 MB at L3 (11,368 series), over the cap. This cluster keeps 6h of data, so the live run did not hit it.

## Harness notes for reading these numbers

- Latencies are measured in-cluster from worker 5 (no port-forward). A "superseded" request is one still running when the page's next poll fires; the UI aborts it, so the harness does the same and counts it as a failure at its elapsed time (a lower bound). The L1 ramp ran before this classification existed and counts those as neutral aborts, so L1's 50-user error rate (51%) is a lower bound; its passing stage (10) does not change.
- The L2 association and 256Mi user ramp were re-run (results in `baseline-L2/`; the first attempts are kept as `superseded-run-*`): the first verifier compared one truth snapshot taken after a CronJob had fired, and the first ramp used the old abort accounting (it ran on to 2,000 users).
- Timeouts at 10 s are TCP connect timeouts while kubesentry was restarting; 30 s and 60 s values are the poll intervals.
- The terminating-endpoint case lives for an hour (preStop sleep 3600). At L2 the verifier ran after it had expired, so that row shows a cluster-side FAIL; the verifier now re-arms it before every run.
- Report sizes for agents: L1 overshot the 50–150 KB target (p50 125 KB, max 200 KB); fixed for L2 and L3 (p50 100 KB, max 150 KB).
